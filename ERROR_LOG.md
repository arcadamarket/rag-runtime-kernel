### E-040: Cross-store status desync — one item carried two contradictory statuses (DONE vs OPEN) with no canonical field
- **Error:** E-022 / E-023 / E-025 (Reddit / Facebook / social-preview) were recorded **DONE** in Cowork memory (`resolved_item_protocol`, S15) but **OPEN — user action** in this ERROR_LOG (S36). Their *true* state was **DEFERRED / on hold** (user, S46). The assistant could not tell which store was right and had to **ask the user** — direct proof the item's status had no single source of truth.
- **Root cause (algorithmic, not a one-off):** (1) Item status is **duplicated as free text across ≥3 independent stores** (Cowork memory, ERROR_LOG summary, per-entry Status lines), each hand-edited, none canonical → guaranteed eventual divergence (classic single-source-of-truth violation). (2) Status is an **unconstrained string** ("done"/"open"/"on hold"/"RESOLVED"/"VIOLATION LOGGED") with **no closed enum and no legal transitions**, so contradictory values coexist undetected. (3) The real lifecycle state **DEFERRED/ON-HOLD was never modeled** for these items, so each store **lossily rounded** it (memory→DONE, log→OPEN). (4) Reconciliation (Rule 11) is a **manual best-effort session-close pass**, not a write-time invariant — i.e. it lives on the exact LLM-judgment surface that drifts.
- **Permanent solution (folds into the drift-elimination layer, surfaces 1–3 + auditor; tracked as DRIFT-ELIM):** (a) **ONE canonical `status` field per tracked item, in the RAG only**; ERROR_LOG / public docs become *renders* of it, never independent authorities. (b) Status = **constrained enum + small lifecycle state machine**: `OPEN → IN_PROGRESS → {RESOLVED | DEFERRED | SUPERSEDED | DISCARDED}`, with `DEFERRED ⇄ OPEN` allowed; exactly one current state.
